# Security audit, 2026-10-21

Epic: #19. Scope: the whole relaynet stack as deployed on 2026-10-21 (rootlessRelay
fork `v0.7.0-hosted.3`, commit `f067524`; relaynet `main` at `e5a728f`).

## How this was done

The review was run as an independent, third-party-style audit: six reviewers,
each with one domain and no knowledge of the others' work, read the code in
full, ran the existing test suites, and wrote small local proofs of concept
where a claim could be confirmed without touching production. Every Medium or
higher finding below was then re-verified against the source by a second pass
before it was accepted. Nothing was run against `relaynet.network`,
`relay.relaynet.network`, Fly, Cloudflare or Auth0; the only live data used
were read-only GitHub API queries (repository settings, secret *names*,
workflow runs), read-only Auth0 Management API queries (applications,
connections, actions, attack protection; no secrets or emails read), and a
comparison of the trusted-proxy CIDR list with Cloudflare's published ranges.

Domains: (1) relay data plane — egress filtering, SSRF, tenant isolation,
rate limits, resource exhaustion; (2) authentication, tokens, organizations,
invitations, the account API, CORS, client-IP trust; (3) operator panel, OIDC,
sessions, CSRF, metrics; (4) web dashboard, headers/CSP, Auth0 SPA
configuration, client library; (5) CI/CD, secrets, container, backups, supply
chain, open-source readiness; (6) metering, audit log, logging, lifecycle,
database layer, privacy-policy conformance.

Not covered (needs live access or is out of scope for this pass): Cloudflare
zone settings (HSTS, R2 token scopes, log retention),
Grafana Cloud retention, Fly 6PN reachability between apps, fuzzing of the TCP
state machine, and an end-to-end exploit of DP-1/DP-2 against a running relay
(the code path and the exhaustion algorithm were confirmed separately).

Severity scale: Critical = unauthenticated or cross-tenant compromise;
High = any authenticated user can deny service to or affect all tenants;
Medium = breaks a stated security invariant or a single tenant's availability,
or materially weakens defence in depth; Low = limited impact or needs an
unusual position; Info = hygiene.

No credential was found in either repository's full history. The controls
that matter most held up: egress deny-list (including cloud metadata, the
host's own addresses and the admin/Litestream ports), no IPv6 or DNS-rebinding
bypass, L2/L3 anti-spoofing between tenants, JWT verification, token hashing
and constant-time comparison, invitation atomicity, role rules, CORS,
parameterised SQL, JSON logging, and the operator SSO allow-list (an ordinary
Auth0 user of the shared tenant cannot become an operator).

The one High and most Mediums are in two places: the DHCP handler in the
shared data plane, which predates the multi-tenant model and escapes it, and
the account API's "pending account" and "operator" checks.

## Findings

Origin: **fork** = exists only in `beriberikix/rootlessRelay`; **upstream** =
the code is shared with `obegron/rootlessRelay` (candidate to report or
upstream, see the last section). Line numbers refer to the commits above.

### Data plane (relay)

**DP-1 — One session can exhaust the shared address pool, permanently. High.**
`relay.js:2095` hands every DHCP datagram to `handleDHCP` before any policy
runs; `handleDHCP` (`relay.js:2302-2353`) allocates by the client MAC *inside
the DHCP message*, not the session's locked Ethernet MAC, and `allocateIP`
(`relay.js:244-265`) has no per-session cap or rate limit. `close()`
(`relay.js:2472-2477`) releases only the session's own MAC, so the extra
allocations outlive the session. A single authenticated session (anonymous
would do, where enabled) can fill the 240-address pool; every later upgrade
from every tenant then fails with 503 "address pool exhausted" until the
process restarts. Confirmed by code and by a reproduction of the allocation
algorithm. Origin: upstream code, fork threat model. Fix: accept only a DHCP
client MAC equal to the session's locked MAC; one address per session; release
everything a session allocated on close; rate-limit DHCP per session.

**DP-2 — DHCP bypasses the anti-spoof ownership checks. Medium.**
`handleDHCP` sets `vmIP` and `ipToSession` directly (`relay.js:2334-2339`)
without any of `claimIP`'s guards (`policy/session_policy.js:271-288`: live
holder, same owner, address holds). A session that knows another session's
MAC can take over its routing entry and originate traffic as that IP. Learning
a MAC across owners is prevented by `canReach`, which limits practical reach
to same-owner sessions and to guessing. Origin: fork. Fix: route DHCP
allocation through the same logic as `claimIP`.

**DP-3 — No UDP destination-port restriction for the user and operator tiers. Low** (re-rated from Medium during remediation).
`allowedUdpPorts: null` (`policy/tiers.js:85-87, 101-103`) and
`EGRESS_DENY_PORTS=[25]` mean a VM can send UDP to any port of any public
host from the relay's egress IP, bounded only by `uploadBps`. That is an
outbound amplification source (NTP, SSDP, memcached, chargen) and an
IP-reputation risk for the shared address. Origin: fork. Fix: in hosted mode
deny the usual amplification ports by default, or move UDP to an allowlist;
add a per-owner aggregate UDP rate.

Re-rating: the relay sends UDP from its own sockets and cannot spoof a source
address, so it cannot reflect amplified traffic at a third party; amplified
replies return to the relay inside the tenant's download budget. Plain UDP
floods are bounded by `uploadBps` exactly as TCP is. What remains is IP
reputation from probing reflector services, hence Low.

**DP-4 — Per-session limits multiply by sessions per owner. Low.** SYN, DNS
and bandwidth limiters are per session (`policy/session_policy.js:136-148`),
so a user with 4 sessions has 4× the advertised budget. Bounded and known;
add owner-aggregate counters if fairness matters.

### Authentication, tokens, organizations, account API

**AU-1 — Pending accounts can manage their personal organization. Medium.**
`requireActive` is called only for token creation (`server/user_api.js:306`)
and invite acceptance (`:483`). A pending account, as owner of its personal
org, can rename it (`:385`), invite active users into it with any invitable
role (`:445`), change roles (`:417`) and remove members (`:505`). Nothing in
`auth/orgs.js` or `auth/org_invites.js` refuses members in `personal=1`
orgs. Confirmed by PoC. Origin: fork. Fix: `requireActive` on every mutating
route except `/api/me/redeem` and `DELETE /api/me`; decide whether personal
orgs may have members at all and enforce it in the store.

**AU-2 — An operator's API token carries operator privilege over the HTTP API. Medium.**
`identityFor` sets `kind: "operator"` from `user.role` regardless of `via`
(`auth/tokens.js:249`); `principal()` (`server/user_api.js:169-171`) then
bypasses membership checks, so a leaked operator *API token* (a credential
meant for VMs) reads every org's member list and pending invitation emails.
Mutations still require a sign-in. Confirmed by PoC. Origin: fork. Fix:
operator privilege only when `via === "jwt"`.

**AU-3 — Anonymous-token issuer keeps an unbounded per-IP map. Low (production: anon off); Medium for deployers with anon on.**
`auth/tokens.js:151-168` prunes only the requesting IP; entries for addresses
that never return are never freed (PoC: 200k IPv6 sources ≈ +47 MiB). Fix:
timed sweep or LRU; key IPv6 by /64.

**AU-4 — Non-object JSON bodies produce 500s that echo internal error text. Low.**
`readJsonBody` (`server/public.js:134`) accepts `null`; handlers dereference
it; the catch-all (`server/user_api.js:544-548`) returns `error.message`,
which would also expose raw SQLite messages. Fix: reject non-object bodies
with 400; generic body for status ≥ 500.

**AU-5 — Accounts are created for JWTs with no or unverified email. Low.**
`email_verified` is required only for invite acceptance; the fallback
username is `<iss>|<sub>` and is never updated (`auth/tokens.js:226-231`,
`auth/users.js:86-91`). Fix: refuse creation when the verified claim is
configured and not true, or update the placeholder on first verified sight.

**AU-6 — Invitation liveness oracle. Info.** 403 `invite-email-mismatch` vs
404 `invite-invalid` tells a token holder the token is live. Deliberate UX
trade-off; acceptable.

**AU-7 — Bootstrap operator name colliding with an existing user crashes the start. Info.**
`admin/app.js:18-27` → `hosted.js:339-341` exits; a restart loop follows.

**AU-8 — Session identity is frozen at upgrade. Info.** Token expiry does not
end a live session (revocation does); JWTs can open sessions, so a dashboard
XSS equals relay access. By design; noted for the threat model.

### Auth0 tenant (live, read-only)

Checked on 2026-10-21 with the Management API: applications, connections and
which applications use them, post-login actions, MFA factors, attack
protection, API (resource server) settings, client grants.

**AT-1 — Email/password sign-up is open on the dashboard and admin applications. Medium.**
The `Username-Password-Authentication` database connection is enabled for
`relaynet-web`, `relaynet-admin` and `Default App`, with sign-up allowed
(`disable_signup: false`) and breached-password detection off. Every real
user signs in with Google. Anyone on the internet can therefore create an
Auth0 user with any email address, unverified, and the relay creates a
pending account for it on first call (AU-5). Not an impersonation path: the
relay keys accounts by `iss|sub`, and invitations require a verified email.
But it chains with AU-1 (a pending account can invite active users into its
personal org), adds a password-spraying surface on the operator client
(brute-force protection and suspicious-IP throttling are on), and lets
anyone fill the `users` table. There is no email provider configured, so
verification mail would go through Auth0's limited built-in sender. Fix:
disable the database connection for `relaynet-web` and `relaynet-admin`
(Google only), or, if passwords are wanted, turn on breached-password
detection and require a verified email before the relay creates an account.

**AT-2 — Leftover `Default App` client. Low.** Tenant default application:
implicit, `client_credentials` and refresh grants, both connections enabled,
`localhost:3000` callbacks, 10-hour ID tokens. It has no client grants, so
`client_credentials` yields nothing, but it can obtain user access tokens for
the relay API: the relay checks `aud` and `iss`, not which client (`azp`)
asked. Fix: delete `Default App`; optionally have the relay accept only the
`relaynet-web` client id in `azp`.

**AT-3 — Refresh-token lifetimes for the dashboard. Info (context for WB-1).**
`relaynet-web` refresh tokens rotate (Auth0 then revokes the family on reuse),
expire after 30 days absolute and 15 days idle; relay API access tokens issued
to the browser last 2 hours. This bounds WB-1 but leaves a 30-day credential
in `localStorage`. If the cache stays in `localStorage`, shorten to about 7
days absolute and 1 day idle.

**AT-4 — No log stream. Info.** Auth0 sign-in and admin logs are kept only for
the plan's short retention; nothing is streamed to Grafana/Better Stack, so
the forensic window for account events is days.

Checked and OK: `add-email-claim` copies `email` and `email_verified` (strict
`=== true`) into the access token; `require-mfa-admin` forces MFA for the
`relaynet-admin` client with `allowRememberBrowser: false`, which answers the
"remembered device" question in AD-6 (no MFA skip); the operator account is
enrolled; factors are OTP, WebAuthn roaming and recovery codes; the admin
client's only grant is authorization code with a client secret; the
dashboard client is a public SPA with authorization code + PKCE and exact
callback/origin lists (`relaynet.network`, `localhost:5173`); RS256 on both
APIs; brute-force protection and suspicious-IP throttling on; clickjack
protection headers on; impersonation disabled.

### Operator panel, OIDC, metrics

No Critical or High. The important question — can a user of the shared Auth0
tenant sign in as operator — is answered no: `admin/oidc.js:127-132` maps the
OIDC identity to a `users.external_sub` row that must already be
`role=operator` and `active`; `amr` must include `mfa` (`:122`); the id token
audience is the admin client. Upstream's admin is an unauthenticated plain
HTTP server bound to localhost, so every control here is fork code.

**AD-1 — Operator username enumeration by login timing. Low** (password
login is off in production). `admin/app.js:37-44` runs bcrypt only for
existing active operators (~2 ms vs ~350 ms); the limiter is keyed
`ip:username`. Fix: always compare against a dummy hash; add a per-IP counter.

**AD-2 — CSRF/DNS-rebinding defence rests on the `Origin` header alone. Low.**
No CSRF token, no custom-header requirement, no `Host` validation,
`SameSite=Lax` (`admin/app.js:178-195`). No working exploit in current
browsers. Fix: require `X-Requested-With` on non-GET `/api`, validate `Host`,
add `frame-ancestors 'none'`.

**AD-3 — `POST /api/users` accepts an undefined tier. Low.** `tier: tier || null`
(`admin/app.js:369-377`) is stored; policy silently falls back to `user`;
unbounded metrics label. Fix: `unknownTier()` check as on the tier routes.

**AD-4 — Inbound rules forward to a pool IP, not a session. Low** (rules are
disabled in hosted mode). `relay.js:2602, 2701, 2745-2763`: after the address
is reused, forwarded traffic reaches a different tenant's VM. Origin:
upstream. Fix: bind rules to a session id and drop them on close.

**AD-5 — Operator sessions survive a password change; no per-operator session kill. Info.**
Demotion/ban take effect on the next request (`deserializeUser` re-reads).

**AD-6 — OIDC issuer taken from the discovery document; refusals log email. Info.**
`admin/oidc.js:112-117, 123, 129`.

**AD-7 — Admin page lacks CSP, `X-Frame-Options`, `nosniff`; sends `X-Powered-By`. Info.**

**AD-8 — `ADMIN_PUBLIC_PATH` is dead configuration. Info.** `hosted.js` never
passes `adminApp` to the public server.

### Web dashboard and client library

**WB-1 — Auth0 refresh and access tokens persisted in `localStorage`. Medium.**
`web/public/app.js:179-191` (`cacheLocation: "localstorage"`,
`useRefreshTokens: true`). Not exploitable alone; it turns any future XSS or
extension compromise into a days-long credential usable off-site. Fix:
`cacheLocation: "memory"` (accept re-login on reload, or set up an Auth0
custom domain so the iframe fallback works), or confirm rotation with reuse
detection and short lifetimes in the tenant.

**WB-2 — Client library reconnects in a tight loop on `1000 "session expired"`. Low. Confirmed.**
`client/relaynet.js:36-41, 231-240` restart with zero delay and reset the
failure count regardless of how long the session lasted; measured ~450
connects/s. The `STABLE_SESSION_MS` guard the comment promises never engages
on this path. Fix: fast restart only when the previous session lasted
≥ `STABLE_SESSION_MS`; otherwise back off. Add a test.

**WB-3 — Invitation token travels in the URL query. Low.** It reaches edge
logs and browser history; `replaceState` happens after the first asset loads
(`app.js:150-161, 710`). Fix: put it in the fragment (`#invite=`).

**WB-4 — Invitation accepted and acting org switched with no confirmation. Low.**
`app.js:788-789, 530-537`. Fix: a Join/Ignore step.

**WB-5 — CSP `script-src` allows all of `cdn.jsdelivr.net`. Low.** The SDK
is pinned (`@2.3.0`) with SRI, but the whitelist neutralises CSP as an XSS
backstop. Fix: vendor the SDK, `script-src 'self'`.

**WB-6 — `?error_description=` text rendered in the status banner. Low.**
`app.js:201-203`, text only. Fix: map `error` to fixed strings.

**WB-7 — Client library accepts `ws://` and may echo the token in a constructor error. Low.**
`client/relaynet.js:20, 51, 167-172, 265-266`.

**WB-8 — `https://beriberikix.github.io` is an allowed origin for the account API. Info.**
`relay/fly.toml:28`; the origin is the whole GitHub account. Drop it if the
demo only needs `checkToken: false`, or document why.

**WB-9 — Header hygiene. Info.** No HSTS in the repo (the zone may add it),
no CSP reporting, `img-src https:` is unused and an exfiltration channel,
the `el()` helper sets unknown keys as properties (`aria-label` bug).

### CI/CD, infrastructure, supply chain

**CI-1 — Production deploy has no approval gate or branch policy. Medium.**
`production` environment: `protection_rules: []`,
`deployment_branch_policy: null`; branch protection is unavailable on a
private free-plan repo. Fix: required reviewer and `main`-only branches on
the environment; rulesets once public; 2FA/passkeys on the account.

**CI-2 — Actions pinned by mutable tag; `setup-flyctl@1.6` installs flyctl `latest`. Medium.**
All workflows; repo setting `allowed_actions: all`,
`sha_pinning_required: false`. Fix: full-SHA pins with Dependabot
`github-actions` updates; pin the flyctl version; restrict to verified
creators.

**CI-3 — Dependabot vulnerability alerts disabled on both repos. Medium.**
`gh api …/vulnerability-alerts` → 404 on both. No `npm audit` or SAST in the
fork's CI. Fix: enable alerts and security updates; add an audit step with an
allow-list; a scheduled check that `relay/package.json` tracks the fork's
latest release.

**CI-4 — `tar`/`node-gyp` critical audit: inert at runtime. Low.** Present in
the image via `sqlite3`, never required at runtime (only
`sqlite3/deps/extract.js` at build). The real exposure is build-time:
`prebuild-install` fetches an unverified prebuilt binary. Fix: `node:sqlite`
(built into Node 24) or `better-sqlite3`; until then document the exception.

**CI-5 — `allowScripts` in `package.json` is not honoured by npm. Low.** It is
a `@lavamoat/allow-scripts` key; `npm ci` runs every install script. Today
only `sqlite3` has one. Fix: `npm ci --ignore-scripts && npm rebuild sqlite3`,
or remove the key.

**CI-6 — Mutable image references. Low.** `node:24-bookworm-slim` without
digest; `fly-log-shipper:latest`.

**CI-7 — Admin port and unauthenticated `/metrics` reachable from every app in the Fly org. Low.**
Staging (password login on) and the log shipper (third-party `latest` image)
share the 6PN. Fix: separate org, or `METRICS_TOKEN`; OIDC-only staging.

**CI-8 — Staging temp-operator password expands into `fly ssh console -C` argv. Low.**
`infra/RUNBOOKS.md:38-41`. Fix: pass it on stdin.

**CI-9 — Relay dependency is a GitHub auto-generated archive. Low.** The
lockfile integrity hash fails closed on any change (good), but the artifact
is not stable; fork `package.json` version is stale (`0.6.0`). Fix: `npm pack`
release asset or a commit-SHA dependency; bump the version per release.

**CI-10 — Production database restored on hosted runners. Info.** Verified: no
artifacts uploaded, counts-only logs, ephemeral runners. Add `shred` in an
`always()` step and environment-scoped read-only keys.

**CI-11 — Backups: no client-side encryption; the relay holds a read-write R2 key. Info/Low.**
A full relay compromise can delete its own backups. Fly volume snapshots are
the independent copy; keep them.

**CI-12 — Fork repo default workflow permissions are `write`. Info.**

**CI-13 — A secret URL is interpolated into a `run:` line. Info.**
`relay-probe.yml:30, 33`. Use `env:`.

**CI-14 — Trusted-proxy CIDR list is a static snapshot. Info.** Identical to
Cloudflare's published lists on 2026-10-21; drift fails safe (per-IP limits
collapse onto edge addresses). Add a scheduled diff.

**CI-15 — `fly.toml` vs `fly.staging.toml` drift. Info.** Documented and
intentional; the GitHub Pages origin is production-only.

### Metering, audit log, logging, lifecycle

**MT-1 — Shutdown flushes before any session close handler runs. Medium. Confirmed.**
`server/lifecycle.js:74-77`: `ws.close()` only starts the handshake;
`flush()` and `exit` follow immediately, so `usage.untrack` (session count)
and `audit.finish` (`ended_at`) never run for open sessions. Effects, on
every deploy: `sessions` under-counted; every open connection keeps
`ended_at = NULL` for its 30-day life, and `audit.query({at})` treats that as
"still open", so an innocent tenant is returned for any later abuse report
about that destination. The shutdown budget is 500/800 ms although Fly grants
15 s. Origin: fork. Fix: run per-session teardown synchronously for every
registered session before `flush()`; raise the timeouts toward the Fly
budget; add a test that `untrack` precedes the flush.

**MT-2 — One failed SELECT wedges an org's quota key until restart. Medium. Confirmed.**
`metering/usage.js:72-87`: `loading.delete(key)` is skipped on rejection, so
after one transient `SQLITE_BUSY`/I/O error every session open and `/api/me`
for that org fails with 500. Fail-closed, so no free service. Origin: fork.
Fix: `finally`; do not cache failures.

**MT-3 — Usage rows for deleted orgs and accounts are re-created by the next flush. Low. Confirmed.**
Rows are deleted before sessions are killed (`server/user_api.js:231-232`,
`auth/orgs.js:110-115, 300-315`); no FK on `org_usage_monthly.org_id`.
Contradicts "removes them immediately". Fix: kill, untrack and flush before
deleting; drop pending entries for the org.

**MT-4 — Quota overrun window. Low.** Enforcement at admission and each 30 s
flush; overrun ≤ ~240 MiB (1.2 %) for the user tier, and it is recorded.
Acceptable.

**MT-5 — Same-owner VM-to-VM traffic is metered twice. Low.** `relay.js:1195,
2419, 1361`. Over-count against the tenant; no egress occurs.

**MT-6 — Unauthenticated clients can write chosen strings into shipped logs. Low.**
Unverified JWT `iss` (`auth/tokens.js:341`), raw `Origin`
(`server/public.js:272`). JSON encoding prevents forgery; this is volume.
Truncate.

**MT-7 — Emails and client IPs in operational logs; the privacy policy names IPs, not account identifiers. Info.**
`server/connection.js:200-206`; `admin/oidc.js:129` logs the email of a
non-user who attempted operator sign-in.

**MT-8 — Admin `/api/usage/:id` reports quota from `users.tier` and only the default org. Info.**
`admin/app.js:798-816`.

**MT-9 — Privacy policy promises a retention hold for investigations; the purge is unconditional. Info.**
`metering/audit.js:148-152` vs `infra/legal/privacy.md:67-68`.

## Privacy policy vs code

Every collection and retention claim in `infra/legal/privacy.md` matches the
code except: the investigation hold (MT-9), usage rows re-created after
deletion (MT-3), account identifiers in logs not mentioned (MT-7), and the
14-day operational-log retention, which is a Grafana Cloud setting that cannot
be verified from the repositories.

## Open-source readiness

Full-history secrets scan of both repositories (provider prefixes, key/secret
assignments, high-entropy strings, ever-committed `.env`/`.pem`/`.sqlite`
files): no real hits. No history rewrite is needed on current evidence; run
gitleaks once more before publication. Before making relaynet public: move
the R2 endpoint (contains the Cloudflare account id, `relay/litestream.yml:21`)
to an environment variable; remove the Better Stack/Grafana identifiers and
the secret digest from `infra/README.md`; consider a `fly.toml.example` so
forks do not deploy to these app names. Auth0 domain and SPA client id are
public by design. See issue #79.

## Recommended order

1. **DP-1, DP-2** — fork fix first (DHCP bound to session MAC, one address per
   session, release on close, through `claimIP`), then offer upstream.
2. **AT-1, AU-1, AU-2** — turn off database sign-up for the two relaynet
   applications (a dashboard setting), then the small changes in
   `server/user_api.js` and `auth/tokens.js`.
3. **MT-2, MT-1** — `finally` in `loadDbTotal`; synchronous drain before flush
   and larger shutdown budget.
4. **CI-3, CI-1, CI-2** — repository settings; mostly clicks.
5. **DP-3, WB-1, WB-2, AU-4, MT-3** — next release.
6. Lows and Infos as hygiene, grouped by file (AT-2: delete `Default App`).

A re-test of items 1–3 should include unit tests that reproduce the PoCs
(the PoC scripts from this audit are throwaway and were not committed).

## Candidates to upstream to obegron/rootlessRelay

Shared data-plane code where the fork's hosted model exposed the issue:

- **DP-1** DHCP allocation keyed by the in-message client MAC with no
  per-session cap or release-on-close — pool exhaustion by one client.
  Upstream is single-tenant, so the impact there is self-inflicted
  exhaustion, but the fix (bind to the session's MAC, release all of a
  session's allocations) is the same and small.
- **AD-4** Inbound rules forward by pool IP, not session — stale forwarding
  after address reuse. Bind rules to a session; drop on close.
- Hardening in shared parsers that the fork relies on (ws `maxPayload`,
  bounded option parsing) is already upstream; nothing to send.

Everything else is fork-only code (auth, orgs, policy, metering, admin
authentication, web).
